## 决策

1. 目录只表达抽象层级：`10_Raw` 原文 / `20_Digest` 摘要 / `30_Canon` 结论。
2. 生命周期（inbox / active / review / stale / promoted / archived）只存在于 frontmatter，任何状态变化都不移动文件。
3. 晋升 = 在更高层新建一篇 + `up:` 回指低层，低层标 `promoted`。
4. 归档 = 把条目从 `catalog.jsonl` 移到 `catalog.archive.jsonl`，文件原地不动。
5. 抽取 = 规则门控与候选提取 → 子代理语义裁判（只喂增量）→ 规则校验落盘。
6. 索引是派生物：`_meta/*.jsonl` 可重建，禁止手改；冲突以笔记为准。

## 理由

- 移动文件是这套系统里风险最高的动作：断双链、git 噪音、状态变化即提交。改成「改字段」后，这些都消失。
- 模型读索引而不是递归扫目录，所以归档的收益可以在索引层完整拿到，物理搬家是纯亏损。
- 规则层承担门控后，LLM 调用量下降约七成，且规则可测试、可回归。

## 放弃的替代方案

- **目录=生命周期**：状态变化就要搬家，双链与 git 历史都会被打碎。
- **三个维度都进目录**：违反唯一归属，必然出现同一篇笔记在多个地方或反复搬运。
- **物理归档到 90_Archive**：断链风险高，收益模型侧仅等于「grep 不命中」，索引分层即可。
- **全量对话直接喂 LLM 抽取**：成本高 15 倍，且会污染主会话上下文。

## 复审条件

- 满 300 篇笔记或 3 个月后复查一次。
- 若 `catalog.jsonl` 超过 3000 行，验证索引分层是否仍然够用。
- 若接入本地嵌入模型（bge-m3 / Ollama），重新评估语义检索与热度的必要性。
