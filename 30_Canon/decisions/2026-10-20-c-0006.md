## 决策

自动注入不是「所有原子都进上下文」，而是由代码强制的三重合取：

```
注入 = core.md
     + level=digest 且 status=active 且 scope ∈ {global, 本会话选定的 project:<slug>}
     （最多 5 条）
```

| scope | 是否自动注入 |
|---|---|
| `global` | ✅ 跨项目通用的用户偏好、原则 |
| `project:<slug>` | ✅ 仅当本会话选中该 slug |
| `system` | ❌ 知识库自身的建设/实现记录 |
| `unclassified` | ❌ 判不准，失败即关闭 |

| status | 是否自动注入 |
|---|---|
| `active` | ✅ 已确认 |
| `inbox` | ❌ 裁判刚写入、未确认 |
| `review` / 其他 | ❌ |

## 理由

- 曾出现真实问题：知识库只记录自己的建设过程，15 条原子里 13 条是施工日志，全部被无差别注入，污染每一轮对话。
- 软约束（提示词里写「不要记系统实现」）是概率性的，且无法纠正已写入的内容；放在检索侧的代码规则是确定性的。
- 失败方向很重要：分类判错只会「少召回」，不会「污染对话」；前者可恢复，后者写入即不可撤销（`10_Raw`/笔记只增不改）。
- `scope` 与 `status` 是两个独立问题——「这条属于谁的记忆」与「这条可信吗」。只设一个闸门不够。

## 放弃的替代方案

- **只靠提示词约束裁判**：模型可能不遵守，且历史条目无法纠正。
- **按目录分区（system 目录 vs 用户目录）**：同样依赖写入侧判断，且检索时还要记住两套路径；字段过滤更直接。
- **只做 status 或只做 scope**：单一闸门挡不住两类不同性质的错误。

## 复审条件

- 若出现「需要临时让 system 类条目进入对话」的场景，通过显式会话范围（`project:` 或临时确认）解决，不要放宽默认规则。
- `project:<slug>` 默认不选中任何项目；多项目并行时才启用选择器。
