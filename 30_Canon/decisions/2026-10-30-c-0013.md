# 多项目记忆库与全局偏好

## 决策

把原来的单 vault 记忆库拆成两层，但**不拆成两个互不相干的产品**：

1. **全局偏好库**（默认 `~/.dsh-memory/global`）：只放称谓、硬偏好、绝对禁区等跨项目适用的 `scope: global` 记忆。每轮最多注入 2 条。
2. **项目记忆库**（默认 `<project>/.dsh-memory/`）：放项目决策、当前状态、施工记忆，`scope: project:<slug>`。每轮最多注入 3 条 + 项目 work brief；`project.json.slug` 是 scope 的唯一来源。
3. **显式接入**：项目库必须由用户运行 `kb attach` 写入用户级 `projects.json`；克隆仓库自带的 `.dsh-memory/` 不会被自动读取，避免 prompt injection。
4. **引擎统一**：`kb.mjs --root DIR` / `KB_ROOT` 选择库；`init` 可初始化项目库或全局库；`attach` 写登记表。legacy vault 仍作为显式信任的项目库保留，旧全局 scope 行为不变。

## 理由

- 用户真正需要的是“跨对话记得住我的习惯”和“这个项目做到哪了”，不是每换一个项目就重建一套知识库。
- 全局偏好与项目记忆的生命周期不同：偏好长期稳定，项目状态经常变化；混在一起会让项目施工日志污染全局注入。
- 项目库必须显式接入：`.dsh-memory/` 是仓库内容，可被 clone/PR 注入；自动加载等于把不可信仓库文本放进系统上下文。
- 每轮 5 条总预算不变：全局 2 + 项目 3；没有全局库时项目可用 5，保持 legacy 行为与旧测试口径。

## 放弃的替代方案

- **继续单 vault，用 scope 区分项目**：无法跨项目自动携带，且项目工作目录没有自己的库，换机/清理都不方便。
- **项目库全部放用户目录**（如 `~/.dsh-memory/projects/<hash>/`）：不随项目走，项目迁移/分享时记忆丢失；与“每个项目带一个库”目标不符。
- **自动发现任意 `.dsh-memory/`**：最简单但最危险；恶意仓库可写入自己的“记忆”并让模型读到。
- **全局库和项目库使用不同引擎/格式**：维护成本翻倍；当前 schema、测试、导出都可复用，只改根与信任层。
- **首阶段就做外部项目写入/自动抽取**：写入路径、队列、裁判、脱敏都要按库隔离，风险大；先验证只读注入与显式接入，再扩展写入。

## 不变量

1. 没有合法 `project.json` 的目录不是项目库；没有出现在用户级 registry 的项目库不加载。
2. 全局库不存项目私有决策；项目库不自动向全局晋升。
3. 项目记忆只注入当前项目 scope；全局记忆注入所有会话。
4. 每轮记忆预算仍是 5 条（全局 2 + 项目 3；无全局库时项目 5），work brief 不占预算。
5. 项目库默认只读注入；捕获/裁判写入仍只对 legacy vault 开启，直到单独实现库级写入。
6. 外部项目库的路径与 token 不写入公开快照；`10_Raw` 默认不进 git。

## 待决

- 项目库放项目内还是用户目录：当前默认项目内 `.dsh-memory/`，用户可改。
- 项目库默认只读还是可写：当前默认只读注入，写入留待后续阶段。
- 全局库由用户显式 `kb init --root` 创建，插件不自动创建（写入只发生在用户明确指定的路径）。

## 复审条件

- 出现多项目并发写入/裁判竞争时，重新设计队列与锁。
- 项目库需要跨机器同步时，评估 git remote/导出策略，不把公开快照当备份。
- 用户实际使用中项目记忆被污染或误注入时，收紧为“项目库需人工确认后每轮加载”。
- 全局偏好数量超过 2 条预算时，优先改注入排序/确认机制，而不是扩大预算。

## 验收

```powershell
node _meta/plugin/kb-panel/test/stores.test.mjs      # 6/6
node _meta/scripts/kb.mjs init --root <tmp>\.dsh-memory --slug demo
node _meta/scripts/kb.mjs --root <tmp>\.dsh-memory attach --registry <tmp>\projects.json
node _meta/scripts/kb.mjs --root <tmp>\.dsh-memory validate
```
