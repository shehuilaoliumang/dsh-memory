# 记忆模型 v2：单一上下文解析与引擎解耦

> 2.0.0 是**结构版本**：用户数据、CLI 命令与注入行为不变，变的是模块边界与决策位置。它回应第十二/十三轮复审的两项结构性债务——架构面 5.5、可继承性 4.0：同一个「这个会话能看哪些库、能写哪个库」的判断在插件里被复制了多份，规则层又整体挂在 DSH 插件内，其他宿主无法复用。

## 背景

- 复审 12/13：行为与安全项已收敛，剩余问题集中在结构上。架构面 5.5、可继承性 4.0 的原因不是功能缺失，而是**决策位置分散**：插件里同时存在 `within(root,cwd)`、`writableProjectStore`、workspace kind 判断与 legacy 特判，任何一处漂移都会让注入/写入路由与文档不一致。
- 规则层（校验、索引、写入、检索、多库、脱敏、工作页）与 DSH 插件耦合：复用规则层必须加载插件，违反「引擎不认识宿主」的分层目标。
- 本轮不改行为；A/B 两条线只做收敛与解耦。

## 决策

### A：单一上下文解析（context.mjs）

- **单一入口**：`_meta/engine/lib/context.mjs` 是「会话看到哪些 store、能写哪个 store」的唯一决策点。插件不再自行推导路径或 kind。
- **统一 store 描述**：`describeStore({root, kind, entry, meta})` 对 global / legacy / project 返回同形描述（`root`/`kind`/`slug`/`scope`/`writable`），`scope` 规则收口为一处：project 有 slug 时为 `project:<slug>`，其余为 `global`。
- **单一写权限**：`resolveWriteTarget(cwd, opts)` 是唯一写权限函数——可写且已接入的 project store 优先，其次 cwd 位于显式配置的 legacy vault 内则写 legacy，否则 `null`（fail closed，不隐式建库）。
- **legacy 数据化**：legacy 不再是散落在插件里的路径特判，而是 `describeStore(kind:'legacy')` 的一种普通 store；`isInsideLegacy` 只作为 resolver 的输入，不作为调用方的分支条件。
- **消费面收敛**：插件 mode/scope 路由、turn-end 写入路由、external ingestor 谓词、attach/relocate、workspaceState 均改用 context 结果；删除插件本地的 `within` 复制与 `writableProjectStore` 重复判断。
- **行为不变量**：vault 内 5 条注入、外部项目 core+3+brief+global 2、写入路由、rename/relocate/promote/delete 语义全部不变；两个 ingestor 实例仍按 store 各建一个，但它们「写不写、写哪里」只由 context 决定，实例数量是内部实现细节。
- **新增测试**：`_meta/plugin/kb-panel/test/context.test.mjs` 5 条（legacy / 可写项目 / 只读 / 未接入 / kind 信任边界），总单测 149/149。

### B：引擎解耦（@local/kb-engine）

- **规则层抽出**：规则层整体迁到宿主无关的 `_meta/engine/`（包名 `@local/kb-engine`）：`bin/kb.mjs` → `lib/cli.mjs`（原 CLI 全量迁移），`lib/stores.mjs`、`lib/work-brief.mjs`、`lib/redact.mjs`、`lib/promote.mjs`、`lib/context.mjs`、`lib/shared/frontmatter.mjs`、`lib/shared/work-sections.mjs`、`lib/index.mjs`，加 `package.json` 与 README。
- **零 DSH 依赖**：engine 不 import 任何 DSH API 或插件代码，只认「store 根目录 + `_meta/config.json`」；root 由 `--root` / `KB_ROOT` / `KB_DEFAULT_ROOT` 决定。
- **双接口**：CLI（`node _meta/engine/bin/kb.mjs --root <store> <command>`）供宿主/脚本进程调用；模块导出（`lib/index.mjs` 与 `exports` 子路径）供宿主进程内 import。
- **兼容包装**：`_meta/scripts/kb.mjs` 保留为 20 行包装（只设置默认 root 并转 engine CLI），所有文档、插件、测试、冒烟继续调它；新集成应直接用 engine 路径。
- **插件 shim**：`_meta/plugin/kb-panel/{stores,work-brief,redact,promote}.js` 与 `shared/*.mjs` 改为 re-export shim，仅作兼容；实现只在 engine。
- **单向依赖**：依赖方向固定为 **engine ← plugin**（插件依赖引擎，引擎不依赖插件/DSH）。
- **闸门扩展**：`check-plugin-load.mjs` 增加 engine 清单与版本一致性、11 个 engine 文件存在性、全部 JS `node --check`；当前口径 6 JSON / 14 manifest / 11 engine / 2 locale / 25 JS。

## 兼容与迁移

- **无数据迁移**：笔记、索引、registry、`_meta/state/` 格式与语义不变；`validate` 仍为本地 3 篇/2 行、公开快照 2 篇/1 行、0 警告。
- **路径变化（实现位置）**：

| 旧路径（v1.x 实现） | v2.0 位置 |
|---|---|
| `_meta/scripts/kb.mjs`（脚本即实现） | 兼容包装 → `_meta/engine/bin/kb.mjs` / `lib/cli.mjs` |
| `_meta/plugin/kb-panel/stores.js` | 实现迁 `_meta/engine/lib/stores.mjs`；插件同名文件为 shim |
| `_meta/plugin/kb-panel/work-brief.js` | `_meta/engine/lib/work-brief.mjs`；shim |
| `_meta/plugin/kb-panel/redact.js` | `_meta/engine/lib/redact.mjs`；shim |
| `_meta/plugin/kb-panel/promote.js` | `_meta/engine/lib/promote.mjs`；shim |
| `_meta/plugin/kb-panel/shared/frontmatter.mjs` | `_meta/engine/lib/shared/frontmatter.mjs`；shim |
| `_meta/plugin/kb-panel/shared/work-sections.mjs` | `_meta/engine/lib/shared/work-sections.mjs`；shim |

- **CLI 不变**：所有命令、参数、`--json` 输出与退出码保持不变；只新增 engine 入口与模块导出。
- **为什么是 major（2.0.0）**：内部模块位置与依赖方向变化属于 breaking change（外部若按旧路径 import 插件文件会拿到 shim 而非实现），但用户数据、CLI 调用与注入行为不变，因此是「结构性 major」而非功能大版本。

## 残余风险

- **shim 是待清理债务**：插件同名文件与 `shared/*.mjs` 的 re-export 只是过渡层，长期应由消费方直接 import engine；清理前必须确认无外部引用。
- **CLI 是进程边界，不是进程内库**：进程内复用请走 `lib/index.mjs`；CLI 适合脚本/其它宿主，但每次调用有进程启动成本，且不能共享内存状态。
- **多库面尚未合并为单库**：global/legacy/project 仍是分离 store，context 只是统一描述与路由；没有做成「一个数据库多租户」，多库的备份/迁移仍需按库处理。
- **DSH 适配层仍在插件**：触发器、HTTP、UI 与 ingest/judge 编排仍属 DSH 插件；engine 只覆盖无宿主依赖的规则与上下文，可继承性提升有限但方向正确。

## 复审条件

- 若出现注入/写入路由与 context 决策不一致、或在插件里重新长出第二份路径/kind 判断 → 回滚相关改动并把分支收回 context。
- 若外部宿主仍需加载 DSH 插件才能使用规则层 → 说明解耦未完成，按缺口补 engine 导出。
- 若 shim 被外部广泛依赖、无法清理 → 评估保留 shim 为长期公开 API 并补文档，不再视作债务。
- 多库合并为单库、或 engine 出现 DSH/插件反向依赖时，重开本决策。

## 关联

- 本决策是实现层结构变更，不推翻 c-1001（授权/迁移边界）的行为语义；c-1001 引用的更早历史 `bdf14e3` 是本地私有仓库历史，公开仓库不可解析。
