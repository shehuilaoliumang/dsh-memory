# 记忆页手动记录与注入可解释

> v2.1 的产品目标从「工具链合格」转向「记忆真正可用」：先让用户能一键把一段话变成待确认记忆，再让用户看见本轮到底注入了什么。两者都不得绕过程序里已有的信任边界。

## 背景

- v2.0 之后复审 82 分、程序性欠账清零，但真实注入几乎为空：全局 2 条偏好、legacy 0 条 digest、3 个项目库 0 条。系统「能记」但「没在用」。
- 记录入口只有自动管线（turn/end → 抽取门控 → 裁判 → inbox）。用户看到一条值得记的内容时没有手动通道，摩擦大；同时用户无法确认「本轮到底注入了哪些记忆、来自哪个库」，对黑盒注入缺乏信任。
- 两项都是产品能力，不是权限模型变更；但手动写入与可解释清单都必须服从既有写路由与确认闸门，不能成为绕过。

## 决策

### 手动记录（`POST /kb/remember`）

- **只写当前可写库**：写入目标由记忆页当前查看的 workspace 决定，且必须可写；路由复用既有的 `workspaceWriteTarget`，最终写权限仍只由 `context.resolveWriteTarget` 决定。只读库/未接入库拒绝。
- **默认 inbox**：手动记录只生成 `add-atom` 的 inbox 原子（`tags: ['manual']`，备注「手动记录（记忆页）」），**绝不直接 active**；必须经记忆页人工确认后才可能注入。手动入口不调用裁判，也不绕过裁判/注入闸门。
- **scope 与库一致**：legacy/global 视图写 `scope: global`；项目视图写 `project:<slug>`；不提供跨库写入。
- **输入约束**：正文非空、≤4000 字；标题缺省取首行前 60 字，summary 缺省取正文压缩前 40 字；type 缺省 `fact`。
- **通道**：仅经 `add-atom --json-file`（唯一原子写入通道），spec 临时文件写在目标库 `_meta/state/` 并即用即删。

### 注入可解释（`/kb/panel.json` 的 `injection` manifest）

- **只读透明**：snapshot 新增 `injection`（`total`/`global`/`project`/`entries`），entries 为 `id`/`summary`/`scope`/`store`（`global`/`legacy`/`project`）。记忆页「本轮注入」折叠卡按此展示。
- **与 prompt 同源**：manifest 与 systemPrompt 注入、计数共用同一个 `selectInjection`/`injectionManifestFor`，面板不可能显示与真实注入不同的集合。
- **不改变选择**：本版只做可见性，不新增 pin/exclude、相关性排序或预算调整。
- **客户端**：build `2026-11-02-c37` 提供「记一条」对话框（空态引导按钮）与「本轮注入」折叠卡。

## 边界与残余风险

- **手动记录无 judge 过滤**：内容质量完全依赖人工；风险由「只写 inbox + 必须确认」兜住；若将来支持直接 active，必须另立决策并补护栏。
- **manifest 只覆盖选择结果**：不含排序理由/权重/预算余量，也不展示未注入的候选；「为什么没注入某条」仍需查 `consolidate`/`search`。
- **不解决注入质量本身**：相关性注入、pin/exclude 仍待 2.2；2.1 只是让「已注入什么」可见。
- **跨库面未合并**：legacy/global/project 仍是不同 store，手动记录只作用于当前查看库，不会触发库间迁移或复制。

## 复审条件

- 若手动记录出现「绕过确认直接注入」「写入非当前可写库」「项目视图写 global scope」→ 回滚相关路由并重开本决策。
- 若 manifest 与真实注入不一致（集合/计数/来源任一项）→ 视为可解释性失效，修回同一 `selectInjection` 入口。
- 当 2.2 引入 pin/exclude 或相关性注入时，本决策的「只读透明」边界需要扩展，届时重开并补排序理由/权重说明。
