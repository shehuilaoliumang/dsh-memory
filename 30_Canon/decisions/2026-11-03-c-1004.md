# 2.2：记忆控制、相关性注入与库面策略化

> 2.1 把记忆「用起来」，2.2 解决「可调、可解释、可继承」：让用户能对**本会话**固定/排除某条记忆，可选按最近对话相关性排序，把整理报告变成可执行动作；同时把多库面的行为从 `legacy` 特判收敛为 policy 字段，并让 engine 支持进程内调用。所有能力都不改变「默认安全」的注入与写入边界。

## 背景

- 2.1.0 发布后，P2 只完成「注入可解释」；复审与使用反馈剩下的问题集中在：无法对单条记忆做会话级控制、排序只看热度不看相关性、整理只有报告没有动作、多库面仍靠 `legacy` 分支、engine 只能通过 CLI 进程调用。
- 这些能力彼此耦合：相关性排序必须先有稳定的注入选择入口，整理动作必须走统一批量写入，进程内 API 又要求 CLI 与模块共享同一实现且不污染宿主进程状态。
- 2.2 的做法是「加能力但不放宽默认」：控制是会话级临时态、相关性默认关、整理动作只执行人工确认的批量操作、库面合并只换表达不换数据。

## 决策

### 会话级记忆控制（pin / mute）

- 新接口 `POST /kb/session/memory`：只认 live session；`id` 必须匹配笔记 id 格式；`pinned` 与 `muted` 互斥（设置一个会清掉另一个）；支持 `value:false` 取消。
- **ephemeral**：控制只保存在 Host 内存，进程重启即清空，不写笔记、不改 `status`/`scope`/正文；因此不会静默变成持久策略。
- 生效范围只有本会话的注入选择：pin 的条目优先保留、mute 的条目从本会话候选中移除；panel 快照 `session.memoryControls` 回显，注入卡给固定标识。

### 相关性注入（带开关，默认关）

- 排序模式由 `_meta/config.json` 的 `inject.rankMode` 控制：`heat`（默认，历史行为）或 `relevance`；`relevanceMaxAgeMs` 控制最近消息的有效期（默认 30 分钟）。
- 相关性打分是插件内纯模块 `memory-rank.mjs`（CJK bigram/ASCII token、覆盖率评分）：相关性优先、热度兜底；最近人类 user 消息只经 `session/event` 捕获（≤800 字、最多 100 会话），不是第二份 transcript。
- **prompt 与 panel manifest 同源排序**：选择函数只有一个，manifest 展示的就是真实注入集合；默认关，避免在无 A/B 证据时改变已有排序。

### 整理动作（只执行人工确认的批量）

- `/kb/consolidate` 返回明细（`stale`、`duplicateSummaries.items`、`readCandidates`、`work`），报告本身只读。
- 记忆页「整理」对话框把报告变成动作：归档过期、归档重复的旧副本、确认热候选；全部走 `/kb/atoms/batch`（既有批量写入通道），不做任何后台自动整理。
- 引擎 `duplicateSummaries` 增加 `items`（id+updated），保留 `ids` 兼容旧消费方。

### 库面策略化（legacy → policy）

- 行为不再按 `legacy` 特判：legacy 用 `policy = { scopeMode: 'global', injectLimit: 5, trustedBy: 'config' }` 表达；普通 project 用 `scopeMode: 'project'` + `injectLimit: 3`。
- `kind` 保留 `global`/`project` 作为标识；legacy 只是 UI/身份标签，注入预算、过滤、简报、core 标签统一读 policy；registry 行携带 `policy`，`findProjectStore` 为 legacy 根合成 config 策略 entry，`writableProjectStore` 不再排除 legacy。
- `resolveContext`/`resolveWriteTarget` 输出 `role`/`trustedBy`，写权限决策仍只有 `resolveWriteTarget`；`globalScopeStore` 保留旧引擎兼容直到 Host 重启。

### 进程内 engine API

- `runCli(argv, { root })` 执行单条命令并返回 `{ code, stdout, stderr }`，不触碰 `process.exitCode`/宿主 stdout；`createEngine({ root }).run(argv)` 是其状态化门面。
- **同步、单线程、单根顺序**：一个模块实例按调用顺序服务；不保证重入并发，不要在命令内部再次 `run()`。
- `bin/kb.mjs` 与 `_meta/scripts/kb.mjs` 退化为薄入口；`lib/index.mjs` 导出 `runCli`/`createEngine` 与共享 parser（补上 `stripFrontmatter` 实现）。

## 边界与残余风险

- **相关性默认关**：`rankMode` 默认 `heat`，A/B 有证据后再切换；相关性排序只影响选择顺序，不改变预算与安全过滤。
- **手动记录仍无 judge 过滤**：沿用 c-1003「只写 inbox + 必须确认」；pin/mute 不改状态。
- **policy 兼容旧引擎缓存**：Host 热重载后若仍缓存旧 engine 模块，`globalScopeStore` 兜底旧行为，直到完整重启；不是长期兼容承诺。
- **算法优化未做**：FEATURES §10 列出的热度自反馈（inject 降权）、exploration 槽、access 热度聚合、字段化 BM25、服务端检索仍待 2.3 评估。
- **进程内 API 不是并发库**：单线程顺序、单根状态；多根并发请用多进程或多次 `runCli`。
- **DSH 适配层仍在插件**：slots/hooks/systemPrompt 与 UI 仍属插件，engine 只覆盖规则与进程内命令面。

## 复审条件

- 若 pin/mute 影响到其它会话或写入笔记状态 → 视为越权，回滚并重开本决策。
- 若相关性模式在未获 A/B 证据时被设为默认、或 manifest 与真实注入不一致 → 回退 `heat` 并修复同源选择。
- 若整理动作出现「未经人工确认的写入」或绕过 `/kb/atoms/batch` → 回滚动作入口。
- 若 policy 合并导致 legacy 注入预算/过滤变化、或 registry 丢 policy → 重开并回退到独立 kind 表达。
- 若 `runCli` 污染宿主进程状态、或并发调用出现串扰 → 收窄为显式 `createEngine` 单实例顺序使用，并补回归。
