# 2.4：检索回退、注入可解释与多库统一视图

> 2.4 处理三个「用户能直接感知但此前只有局部能力」的缺口：全文检索只能命中字面词；记忆页能看到哪些注入了、看不到**为什么没注入**；工作区选择器能看单个库，不能只读地看全部库。三件事都不改变写入授权、注入预算和 fail-closed 规则。

## 背景

- **检索召回窄**：2.3 的 BM25 是字面词 + 中文 bigram；用户输入拼音（`jiyi`）或同义词（`上线` 对「发布」）时命中为零，明明库里有对应记忆。
- **注入不透明**：panel 只给「本轮注入」清单（最多 5 条），其余笔记为何落选只能靠读代码；这既难排查「这条怎么没进来」，也容易让用户误以为库坏了。
- **多库没有统一面**：全局库、legacy 知识与 3 个项目库各自独立；要跨库找一条记忆必须反复切换选择器。合并读视图必须**不改变任何写入/注入路径**。

## 决策

### 拼音与同义词回退（只在检索层，字面命中优先）

- **拼音**：把 tiny-pinyin 1.3.2 的字典与算法以 MIT 许可 vendored 到 `_meta/engine/lib/search/pinyin.mjs`（约 8 KB，6763 常用字，无运行时依赖）；`toPinyin` 产出全拼与首字母，ASCII 查询（如 `jiyi`）在字面 BM25 无结果时回退到拼音匹配。附 `PINYIN-NOTICE.md` 保留 MIT 与上游 HanziToPinyin/Apache-2.0 归属；`Intl.Collator` 不可用时降级为空结果，不抛错。
- **同义词**：`_meta/engine/lib/search/semantic.mjs` 维护 21 个中英双语主题组（发布/上线/deploy、删除/移除、检索/搜索、注入/上下文…）；`expandQuery` 只在整词命中 ASCII 别名、或中文别名长度 ≥2 时扩展，单组最多 4 个、总计最多 10 个新词，已存在的词不重复。
- **排序与边界**：字面 BM25 结果始终在前并标 `matchedBy:'literal'`；拼音/语义回退结果去重后**只在字面结果不足 `min(limit, 3)` 时补位**，语义分数 ×0.5，均标 `matchedBy`/`matchLabel`/`matchTerms`；响应新增 `strategy:{pinyin,semantic}`，客户端显示「（拼音兜底 + 同义扩展）」。回退是**召回辅助**，不写 access、不改注入、不替代字面检索。

### 逐条注入原因（咨询性，不参与选择）

- `_meta/engine/lib/injection-reasons.mjs` 新增纯函数 `explainInjection({notes, entries, scope, viewKind, mutedIds, inSessionStore, limits})`；它读取**同一份** manifest entries、同一套 `isInjectable` 与同一组预算上限，为每条笔记给出 `{state,label,detail}`。
- 判定优先级：不在当前会话（其他库只读视图）→ 已注入 → 本会话静音 → status（inbox/review/archived/promoted/superseded）→ 非 digest 层（canon/raw）→ 页面类型（topic/work/session）→ fail-closed scope（无 scope/项目隔离/范围不符）→ 同 subject 有更新 → 预算已满 → 本轮未入选。
- 仅供解释：**不改变注入结果**；panel 快照把 `notes[].injection` 下发，记忆页列表显示短标签、详情显示「标签：原因」，注入中的条目显示「已注入」。预算原因带「全局 G / 项目 P / 总计 5」，避免出现「为什么别的条目能进」的误解。

### 多库统一只读视图

- 选择器在已有 >1 个工作区时前置「全部记忆库」；客户端并发拉取各库 `panel.json` 并按 `uid = workspaceId::noteId` 合并，**不新增服务端合并写入接口**，各库的注入计数、信任标记、写权限完全不动。
- 统一视图 `view = {id:'all', kind:'all', writable:false}`：隐藏「记一条/整理/改名/接入」等写操作；列表标来源库，详情标「来源：…」；点开详情时带 note 所属工作区，走既有 `/kb/note.json` 白名单读取。
- 深度搜索传 `workspace=all`：服务端遍历 `workspaceOptions()`，每个库仍用该库自己的 engine + scan id 白名单过滤，结果行带 `workspace/workspaceLabel`，全局上限 20；只读、不写 access。
- 同库 id 冲突用 `uid` 命名空间隔离；单库视图的 uid 改用**选择器 id**（legacy 的展示 id 与内部 slug 不同），保证选择、详情、深度搜索三者一致。

## 边界与残余风险

- **不是通用语义搜索**：没有 embedding；同义词表是人工维护的有限集合，未收录的主题不会扩展；拼音不支持多音字（曾/沈按字典固定读音），首字母回退存在碰撞，只作为字面结果不足时的补位。
- **`Intl.Collator` 依赖**：pinyin 模块在缺少 zh 排序 ICU 数据的运行时降级为空结果（不报错、不回退到错误读音）。
- **解释可能与实际选择漂移**：`explainInjection` 只消费 manifest；若未来新增注入来源但不更新该函数，原因会滞后。复审条件要求两者同改。
- **统一视图是只读合并**：不提供跨库写入、批量移动或跨库去重；重复笔记会在视图中同时出现（按来源可辨）。
- **性能**：all 搜索按库串行执行 engine CLI，库数增长会线性变慢；限制每库 limit 与总 20 条，暂不并行，避免多个 node 子进程同时争用。

## 复审条件

- 拼音/语义回退把字面命中挤到后面、或对不存在查询仍报命中 → 回退逻辑视为错误，恢复字面优先。
- 回退结果写入 access、或返回未 scan 的路径/id → 视为越权，回滚 API。
- `notes[].injection` 为「已注入」但 manifest 中不存在、或未注入条目被标为已注入 → 解释层与选择层漂移，必须同改。
- 统一视图出现任何写入口、或合并后能读到未授权库的详情 → 立即关闭该视图。
- 多音字/首字母误召回成为常态、或库数增长使 all 搜索明显卡顿 → 重新评估拼音词典与并行策略。
