# 3.2：记忆智能增强（候选、确认、预算、健康、检索）

> 第 18 轮外审 86 分、无新增修令后，用户对“实用性中上”的追问选择“1–5 全做”。五项都围绕一个目标：让已有记忆更容易被正确写入、确认、选中和检索，而不是增加新的写入权或改数据模型。

## 背景

3.0/3.1 已统一读面与三宿主，但实际使用仍暴露五个摩擦点：裁判候选缺主题/取代/scope 建议；确认只能逐条点；注入预算固定且用完即止；没有记忆库健康视图；检索仍是字面 + 拼音 + 人工同义词。用户明确要求五项一起做，且接受一次行为 minor（3.2.0），完成后回冻结维护。

## 决策

### 1. 候选建议与可选自动确认（candidates + judge）

- 新增 `_meta/engine/lib/candidates.mjs` 纯函数：显式记忆检测、文本相似度、subject/supersedes/scope 建议、反馈汇总、autoActivate 判定与审计串。
- 裁判仍只产出候选并默认 `inbox`；建议写入原子 `note`，不改变 scope/status。
- `judge.autoActivate` 默认关闭；开启后也只对“显式记忆 + 项目库 + scope 匹配 + 无 pending supersedes + 置信度/反馈阈值”自动 `active`；global/system 永不自动，显式优先于软提示。
- 审计串记录“为何自动/未自动”，便于回查；自动 active 仍走 `add-atom` 同一通道与同 subject 冲突拦截。

### 2. 批量确认与会话反馈复用

- 面板列表增加多选与“批量确认/归档”，经既有 `POST /kb/atoms/batch` 执行；不新增旁路写通道。
- 每次 `active`/`archived` 迁移继续写 `_meta/state/judge-feedback.jsonl`，聚合为 accept rate 供 autoActivate 阈值使用；拒绝不删除内容。
- 批量动作仍逐条校验同 subject/scope；单条失败整批拒绝，不做半批静默。

### 3. 自适应注入预算、建议与排序实验

- 读面在 base `global 2 / project 3 / total 5`（legacy project 5）上，把未用总槽回填给另一来源的溢出候选；global 硬上限 4，total 仍 5，prompt/panel/manifest 同源。
- `injection.suggestions` 只列“预算已满但排名紧随其后”的前 3 条，作为只读提示，不改变选择、不写 access。
- `inject.rankExperiment` 默认关闭；开启后按 `sessionId + salt` 稳定分桶 heat/relevance，并记录分配；实验不改变默认排序，等真实数据再决定默认。

### 4. 记忆健康（只读）

- 新增 `_meta/engine/lib/health.mjs` 纯函数，输出 10 类问题（冲突、悬空取代、待确认取代、缺 subject、scope 异常、过期、待复审、重复、未分类、低召回），按 error→warn→info 排序。
- 面板只读健康卡显示计数与摘要；不自动修、不删除、不改状态。修复仍由人通过整理/批量动作完成。

### 5. 检索升级（意图 + 同义扩展 + 向量近似）

- `search/intent.mjs` 识别状态/决策/偏好/查询意图；字面命中同类型 ×1.15 重排。
- 字面不足 `min(limit,3)` 时依次回退：拼音 → catalog/同义扩展（最多 4 词）→ 2048 桶 FNV n-gram 向量近似（查询特征 ≥2、候选重合 ≥25%、cosine ≥0.12）。
- 向量是零依赖词频近似，**不是 embedding**；JSON 增 `intent` 与 `strategy.vector`，面板显示意图/向量提示；检索仍不写 access。
- 参数/阈值集中在模块常量，后续可关闭或调参；不引入新运行时依赖。

## 配置

`_meta/config.json` 新增：

- `judge.autoActivate`：`enabled`（默认 false）、`explicitOnly`、`projectOnly`、`minConfidence`、`minFeedback`、`minAcceptRate`。
- `inject.rankExperiment`：`enabled`（默认 false）、`modes`、`salt`。

两项都可随时关闭；关闭时行为回到 3.1.0。

## 验证

- 插件 193/193（新增 rank-experiment 6）；engine 78/78（candidates 15、health 33、search-upgrade 12、read-model 8、host 6、host-conformance 4 等）；脚本 17/17；冒烟 106/106；`check-plugin-load` 7 JSON/9 manifest/23 engine/2 locale/45 JS；本地 `validate` 15 篇/13+1、0 警告；`compare-parity` 0 regression；`bench-read-model` 5×300 检索约 346ms、面板约 125ms、`spawnFree:true`。
- parity 容忍合法新内容：新增 canonical 条目可能把基线检索的末位行挤出 limit 窗口（本轮 c-1008 的 `记忆` 使 `jiyi` 的 c-1004 被置换），记录为 drift；仅当没有任何新行进入时才把基线行消失判为 regression；基线行的元数据与相对顺序仍是硬失败。
- parity 自包含夹具按 3.2 自适应预算改为 5 条（4 global 溢出 + 1 project，global 硬上限 4/total 5），并保留精确顺序断言；把 global 硬上限改小仍会失败。
- CI 在 Node 22 下逐文件跑 engine 测试；parity 无私有库时跑自包含夹具。
- 写入权限/两闸删除/文件布局/frontmatter/registry 全部未改；新行为不新增写路径。

## 风险与边界

- autoActivate 即使开启也可能误判，故默认关闭且只允许低风险项目内显式记忆；global 永远人工。
- 自适应预算可能让来源比例偏离 2/3，但 total 与 global 硬上限不变；prompt/panel 同源，可解释。
- 向量近似可能召回“词面相近但语义无关”的条目，故仅作最后回退，分数门槛 + 面板显示匹配方式。
- 健康报告只读，可能与实际修复动作短暂不一致；以笔记状态为准。
- 所有建议均为 advisory，不构成自动写入授权；物理单库合并仍未做。
